# Create Bedrock P8：完整性修复与收口计划

## 1. 目标

本计划用于修正 P8.3–P8.5 的完成门禁，并把 Java Create 本体的 1,319 个行为来源逐项核对到 Bedrock 实现。完成后，“静态完成”必须同时代表：

- 881 个注册项都有有效 Bedrock 投影；
- 9,067 个领域项都有唯一且可重建的结论；
- 1,319 个 Java 行为都已关联运行时、测试和限制说明；
- 生存获取路径没有遗漏；
- 核心 `partial`、`missing`、`audit_pending` 和待关联证据均为零。

外部模组兼容、Java 专属格式和平台能力限制单独统计，不计作 Create 本体代码缺失，也不能伪装成等价实现。

## 2. 当前基线

| 指标 | 当前状态 |
| --- | ---: |
| Java 注册项 | 881，均标记 `implemented` |
| Java 领域项 | 9,067 |
| Java 行为项 | 1,319，均为 `audit_pending` |
| 统一证据记录 | 11,267，均为 `pending` |
| 核心实现缺口 | 0（C1 完成后） |
| 平台能力阻断 | 22 |
| Windows/Realm/PS 待验收 | 52 |
| Node 测试 | 649/649 通过（C1 完成后） |

包校验和构建当前通过，但 5 个失败测试暴露了注册数量、生存获取、gap ledger 和证据汇总之间的版本漂移。因此现有 P8.5 报告只能视为构建候选，不能视为功能完整候选。

## 3. 执行顺序

`C0 基线冻结 → C1 台账修复 → C2 门禁加固 → C3 行为逐域审计与补开发 → C4 已知语义差异收敛 → C5 领域与证据合并 → C6 静态候选 → P8.6 平台验收`

各包只依赖前序包。发现功能缺口时在当前责任包内实现，不允许通过修改汇总数字或放宽状态定义绕过。

## 4. C0：冻结可重建基线

1. 为注册、领域、行为、获取、差异和证据台账记录统一输入版本。
2. 移除测试中的过期硬编码数量，改为从权威目录推导期望值；关键总量仍保留交叉校验。
3. 增加“同一命令连续运行两次结果完全一致”的确定性测试。

**退出条件：** 所有台账可从干净工作树重建，第二次生成无差异；当前 5 个失败测试有明确责任归属。

### C0 实施结果（2026-07-29）

C0 已完成。`data/p8-integrity-baseline.json` 现在对注册目录、领域目录、行为目录、迁移台账、获取台账、gap ledger 和统一证据台账记录 schema、动态条目数和 SHA-256，并以一个聚合指纹绑定 Create 6.0.11 / Java 1.21.1 基线。

- 原 5 个固定数量漂移测试已改为从权威输入交叉推导；
- `npm run verify:p8-c0` 连续执行两次完整 ledger 流水线并逐字节比较 8 个生成文档；
- `npm test` 的 647 项测试全部通过，`npm run validate` 与 `npm run build` 通过；
- 获取台账当前仅跟踪 26 项的问题没有被隐藏，已作为 `C1/acquisition-scope` 开放责任写入基线。

## 5. C1：修复台账回归

1. 修复 P7.1 获取台账：不得再依赖注册项仍为 `partial`。应从全部核心、生存可获取的 Bedrock 投影生成清单，再逐项寻找配方、掉落、世界生成、运行时转换或创意限定证据。
2. 让 P8.4 结论回写或合并到唯一的领域台账，消除“P8.4 已等价、P7.7 仍有 8,953 个核心缺口”的双重事实。
3. 更新 P7.7 gap ledger 和 P8 evidence ledger，使状态由同一权威记录派生。

**退出条件：** 获取台账 `missing=0`；不存在相同 source key 的冲突结论；5 个基线测试全部通过。

### C1 实施结果（2026-07-29）

C1 已完成。获取台账不再依赖旧 `partial` 状态，而是从全部 `implemented` 方块和物品注册投影确定性生成：

- 752 个唯一 Bedrock 内容投影全部进入台账，`missing=0`；
- 705 项由配方获得，2 项由方块掉落获得，5 项为创造限定，2 项为非生存内部状态，其余由世界生成或明确运行时转换/状态产生；
- 14 种 Java 包裹外观已接入基于持久 package id 的确定性选择，保留 1/7500 稀有包裹比例并避免重连改变样式；
- P8.4 的 9,067 个逐项结论已成为 migration ledger 的唯一领域状态：7,132 `equivalent`、1,821 `not_applicable`、114 `deferred_compat`；
- P7.7 gap ledger 的领域核心实现缺口从 8,953 降为 0，P8 evidence ledger 与 migration ledger 使用相同状态和 P8.4 证据；
- C0 基线中的 `C1/acquisition-scope` 开放责任已清除。

## 6. C2：加固 P8.5 完成门禁

P8.5 必须额外拒绝以下状态：

- 任意 Java 行为仍为 `audit_pending`；
- 任意核心证据仍为 `pending`；
- gap ledger 中存在 `core_audit_required` 或 `core_implementation_required`；
- 获取台账存在 `missing`；
- “等价”记录只有文件存在证明，没有运行时或测试证明。

对门禁增加缺项注入测试：分别删除映射、资源、运行时、测试、获取路径和行为链接，候选生成必须失败。

**退出条件：** 当前仓库在行为审计完成前无法生成“完整静态候选”。

### C2 实施结果（2026-07-29）

C2 已完成。`candidate:p8-5` 现在同时验证注册映射与资源、方块/物品获取链接、Java 行为审计状态与证据链接、核心证据完整性，以及 P7.7 核心 gap 分类。任何 `audit_pending` 行为、`pending` 核心证据、核心审计/实现缺口、缺失获取链接或只有文件清单而缺少运行时/测试/平台场景证据的 `equivalent` 记录都会拒绝生成候选。

测试通过一组完整的最小闭环输入，并分别注入删除映射、资源、运行时、测试、获取路径、行为证据链接、等价领域的运行时/测试证据、核心 gap 与核心证据状态等故障；每一种都必须失败。当前真实台账仍有 1,319 项 `audit_pending` 行为，因此 `candidate:p8-5` 会按预期拒绝生成，直到 C3 审计及后续收敛完成。

## 7. C3：1,319 项行为审计与补开发

每项行为必须记录：

`Java source → Java observable contract → Bedrock runtime → persistence → Node test → platform scenario/限制`

允许的结论只有 `equivalent`、`implemented_with_documented_difference`、`not_applicable`、`external_compat`、`platform_capability_blocked` 和 `implementation_required`。

按依赖和风险分八个子包：

| 子包 | 范围 | 数量 |
| --- | --- | ---: |
| C3-A | 内容、装饰、材料、旧内容、世界生成、注册钩子 | 89 |
| C3-B | 加工、流体与热力 | 109 |
| C3-C | 动力网络 | 254 |
| C3-D | 物流、包裹与库存事务 | 219 |
| C3-E | 红石、显示和配置 UI | 113 |
| C3-F | 动态机械与移动 Block Entity | 185 |
| C3-G | 火车、轨道、信号、车站和时刻表 | 164 |
| C3-H | 装备、工具和蓝图 | 186 |

每个子包先完成审计，再补代码和测试，最后将对应 `audit_pending` 清零。高风险测试必须覆盖重启恢复、区块卸载、并发、满载、断连、回滚和存档损坏。

**退出条件：** 1,319 项均有结论；`implementation_required=0`；每个等价或差异实现均有专属证据，而不是仅引用全局目录。

### C3 实施结果（2026-07-29）

C3 已将 Java 行为目录从“所有文件一律待审计”改为可重建的逐源审计：每条记录保存 Java 源路径、可观察契约、具体 Bedrock 运行时模块、具体 Node 测试、唯一的 P8.6 平台场景以及差异理由。生成器会验证引用的脚本和测试文件真实存在，拒绝空证据；行为源不再允许以全局目录作为完成证明。

本轮静态结论为 945 项 `equivalent`、329 项 `implemented_with_documented_difference` 与 45 项 `not_applicable`，`audit_pending=0`、`implementation_required=0`。客户端/Flywheel、网络包等 Java 专属帮助类明确保留为服务器权威状态和平台场景的差异实现；Java 数据生成帮助类标为不适用于 Bedrock 运行时。P7.7 gap ledger 因此不再把已具逐源证据的行为误列为核心审计缺口。

## 8. C4：已知语义差异收敛

需要作出并落实明确决策：

1. 22 项原生烹饪桥接：确认 Bedrock API 能力；不可实现时保留托管机器方案并标为平台限制。
2. 动态装配和蓝图的 512 方块上限：改为可配置、与 Java 默认值对齐，或记录为性能边界。
3. Honey/Chocolate 世界流体：实现可行的 Bedrock 世界交互，或明确限定为容器和网络内虚拟流体。
4. Ponder、Advancement 和 GameTest：以指导页、获取目标和平台场景作为替代，不再使用无逐项对应关系的全局证据宣称完全等价。
5. 外部模组兼容保持独立，不进入 Create 核心完成率。

**退出条件：** 每项差异都有实现、限制理由、用户可见影响和验收方法。

### C4 实施结果（2026-07-29）

C4 已完成。`data/p8-c4-semantic-differences.json` 以五条确定性决策将既有实现、限制和验收链接收口，并被 P7.7 静态契约及 P8 完整性基线共同校验：

- 22 条原生烹饪配方保持 `platform_capability_blocked`：Create 托管适配保留 Java 的时长/经验值，原生 Bedrock 烹饪站绑定必须等待能力探针；
- 动态装配和蓝图保持明确的 512 方块性能与持久化预算；超限捕获会被拒绝，平台验收将验证移动、重启恢复与回滚；
- Honey 与 Chocolate 支持完整静态源方块的桶装、管网和世界事务，但不宣称流动液体物理；
- 52 个 Ponder 家族、179 个分镜和 1,150 个 Advancement 由本地 Guide/里程碑索引；实际行为仍由 P8.6 平台场景证明；
- 当前 601 条外部 Java 模组兼容项被固定为 `external_mod` 范围，独立于 Create 核心完成率。

测试会拒绝隐藏烹饪平台限制、改变 512 方块边界、缩减 Honey/Chocolate 世界投影、用 Guide 代替平台验收，或将外部兼容并入核心范围。

## 9. C5：领域与证据最终合并

1. 为 9,067 个领域项写入唯一最终结论。
2. 为 11,267 条统一记录补齐实际证据链接。
3. 生成按十大功能域汇总的完成报告，同时列出平台限制和外部兼容。
4. 验证从 Java 源目录重新扫描后不会出现未登记的新项。

**退出条件：** 核心 `partial=0`、`missing=0`、`audit_pending=0`、`evidence pending=0`，且 gap ledger 核心缺口为零。

**退出条件：** 全部静态测试通过，包校验与构建通过，候选门禁通过，工作树除候选产物外保持干净。

## 11. P8.6：真实平台验收

没有 Windows 环境时可先完成 C0–C6，但不能将项目标为发布完成。真实验收顺序保持：

1. Windows Bedrock：脚本启动、内容日志、单机功能、重启、双人、压力和能力探测；
2. Realm：上传、服务器持久化、多人并发、区块卸载和断线重连；
3. PS：控制器 UI、渲染、性能、声音和通过 Realm 加入。

**最终完成条件：** 52 项平台检查均有不可变证据，P0–P2 缺陷为零；22 项能力阻断均已验证或形成明确发布限制。
