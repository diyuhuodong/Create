# P7.4C 动力网络与锅炉设计

## 目标与边界

P7.4C 用 Java `BoilerData` 的可观察语义替换当前 Steam Engine 的固定容量近似。它覆盖 Fluid Tank 锅炉、多方块尺寸、加热器、水供给、多个 Steam Engine 的效率分配、应力网络和重启恢复。它不实现 P7.5 的移动锅炉投影，也不把 Bedrock 世界流体伪装成原版流体模拟。

## Java 行为基线

锅炉由相连 Fluid Tank 的控制器拥有。方块数为 `N` 时，尺寸上限为 `min(18, floor(N / 4))`；水供给上限为 `min(18, ceil(max(最近采样水供给) / 10))`。每五 tick 采样一次供水并保留滚动窗口。Blaze Burner：FADING/KINDLED 贡献 1，SEETHING 贡献 2；被动热源贡献被动热，且只有没有主动热时生效。

实际热级为 `min(主动热, 尺寸上限, 水上限)`。主动锅炉的每个引擎效率为 `1`（引擎数不超过热级）或 `热级 / 引擎数`；被动锅炉总是每引擎 `1/8`。无热或无有效水时效率为零。

## Bedrock 状态与运行时

新增持久化 `BoilerController`，以维度和 Tank 控制器坐标为键。它保存成员位置、采样环、累计供水、主动/被动热、已发现引擎、每个引擎的最后一次 receipt、schema 版本和诊断状态。Tank/pipe 的流体扣除使用 P7.3 `FluidLedger` receipt；重启后只能恢复未完成扣除或输出，不能重复消耗水。

每个 tick：扫描已加载的相连 Tank 成员，读取其下方加热器，计算大小与热级；每五 tick 确认供水窗口；发现连接的 Steam Engine，并将每台引擎的效率映射为 `KineticWorld.setExternalSource` 的速度、容量和方向。应力不足、反向冲突、目标拆除或外部端口失败均输出零动力并保留可恢复诊断，而非猜测继续运行。

## 实施包与验收

1. C1：纯 `boiler-model`、Java 常数和单元测试（尺寸、水、热、效率）。
2. C2：可持久化控制器、Tank 拓扑扫描、receipt 恢复与并发测试。
3. C3：Steam Engine 适配、方向/多引擎/应力/过载测试，移除固定 64/128 容量近似。
4. C4：资源状态、诊断与 Windows Bedrock 手工案例；通过后才进入 Realm 和 PS。

完成口径：热级、供水、尺寸、引擎分摊、过载、拆除与重启都由测试覆盖；不再用水标签或固定常数代表锅炉输出。
